# Shopping Sessions

一家網路商店把頁面瀏覽、加入購物車、購買和廣告點擊記錄成 CSV 檔。這些 log 很髒：有重複、格式錯誤的行、錯誤的時間戳記，以及遲到的事件。一位購物者可能有很多個 user ID，第三個檔案會透過很長的連結鏈與共用裝置把它們串起來。

清理 `/data` 中的 log，合併每個人的 ID，建立 session，把每個 session 歸因到帶購物者進來的那次廣告點擊，計算前一週的輔助（assisting）活動，並寫出兩個每日 Parquet 表（`/output/user_daily/` 與 `/output/campaign_daily/`），一個以人為單位、一個以活動（campaign）為單位。規則是精確的，所以答案只有一個；快但差一點點的答案得零分。

分數是容器執行秒數，越低越好。每小時可以在隱藏的練習資料（約 2,000 萬筆事件）上提交 2 次。決賽約 6,000 萬筆事件，每次執行上限 3 分鐘：任何一次決賽執行超時就沒有決賽成績，所以練習時目標約 60 秒以內。

## 本地開始

下載下方的 `rules.md` 和一個起始專案（PySpark、DuckDB 或 Polars）。任何引擎、任何語言、任何程度的 AI 皆可：Spark、DuckDB、Polars、Rust、C++、純 Python。

每個起始專案都會寫出欄位正確但沒有資料列的兩個表，實作規則由你負責。

1. 實作 `rules.md` 的 pipeline，並通過起始專案的 36 個邊界案例 fixture。
2. 用 `generator.zip` 產生 100 萬筆事件的開發資料集，解壓 `dev-answer.zip`，執行 `make check-dev` 在本地檢查輸出。

## 繳交內容

提交一個根目錄有 Dockerfile 的公開 GitHub repo，以及要計分的 commit。repo 最多 50 MB 且不能放資料，因為資料集會在執行時掛載。

## 容器限制

- 映像檔必須是 linux/amd64，最多 8 GB。建置有網路，最多 10 分鐘；執行時沒有網路。
- 每次執行有 8 個固定的 vCPU（hyperthread）、24 GB 記憶體，沒有 swap。
- `/data` 唯讀，`/scratch` 是可寫的磁碟供溢寫使用。`/output` 與 `/scratch` 合計最多 50 GB。
- 根檔案系統唯讀，只有 `/tmp`（64 MB，在記憶體中）可寫，程式以 uid 1000 執行。
- 環境變數：`DATA_DIR=/data`、`OUTPUT_DIR=/output`、`SCRATCH_DIR=/scratch`、`HOME=/scratch`、`NCPU=8`、`MEM_GB=24`。
- 最多 4,096 個 process 與 thread，stdout 最多 50 MB（log 請寫到 stderr）。

## 文件與起始檔案

- `rules.md`：完整規格：輸入、CSV 格式、清理、ID 連結、session、歸因、輔助與輸出表。
- `starter-pyspark.zip`：PySpark 骨架（linux/amd64、Java、Spark 與測試腳本）；寫出空表。
- `starter-duckdb.zip`：DuckDB 骨架（linux/amd64）與測試腳本；寫出空表。
- `starter-polars.zip`：Polars 骨架（linux/amd64）與測試腳本；寫出空表。
- `dev-answer.zip`：100 萬筆事件開發資料集（seed 1）的預期 `user_daily.csv` 與 `campaign_daily.csv`，供 `make check-dev` 使用。
- `generator.zip`：`generate` 的 Rust 原始碼。可產生 100 萬筆或任意大小與 seed 的資料集。

## 計分

| 項目 | 內容 |
| --- | --- |
| 指標 | 執行時間，越低越好 |
| 要超越的基準 | 172.00 s（Starter：PySpark，local mode） |
| 公式 | 在隱藏資料上執行一次（20 s 以下則取 3 次中位數），從啟動到結束 |
| 同分 | 同分時較早提交者排前面 |
| 計分器版本 | shopping-sessions-4 |

主辦方會建置你的 Dockerfile，在開發資料集上檢查，然後在全新容器中對隱藏的練習資料（約 2,000 萬筆事件）計時一次。20 秒以下的執行會計時 3 次並以中位數計分。

## 規則

- 起始專案與 `rules.md` 衝突時，以 `rules.md` 為準。若 `rules.md` 讓你不確定，請詢問主辦方。
- 每次提交會先在公開的 100 萬筆開發資料集上執行（最多 3 分鐘）。失敗的話，你會拿到不一致的資料列與 log，並就此停止。
- 練習執行最多可花基準時間的 2 倍，且不超過 5 分鐘。計時一次，若第一次低於 20 秒則計時 3 次；重複執行共用第一次的時間上限，被中斷的重複執行以完整上限計。練習資料約為開發集的 20 倍，所以在開發集上超過約 15 秒的作品通常會超過這個上限。
- 表錯誤、崩潰，或觸及記憶體、磁碟、stdout 或時間上限都會讓提交停止。
- 決賽使用約 3 倍的練習資料量，每次執行上限 3 分鐘。任何一次決賽執行超過 3 分鐘就沒有決賽成績，所以練習時目標約 60 秒以內。
- 不同計分機器間練習時間可能相差約 20%，所以練習榜上的小差距沒有意義。
- 隱藏執行不會顯示 log 或資料中的值：只有 exit code、是否記憶體不足，以及缺少、多出與不一致的資料列數。
- 計時從容器啟動到容器結束，包含啟動引擎與讀取 CSV。
- 每隊每小時可提交 2 次。被拒絕的提交不會改變你的最佳分數。
- 在結果公布前，repo 必須保持公開並保留每個提交過的 commit。決賽時無法取得或還原的作品得零分。

## 決賽

截止時，主辦方會重新建置你選定的 commit（預設為最佳，除非另選），在提交截止後產生的約 6,000 萬筆新事件上計時 3 次，每次上限 3 分鐘。任何一次超過 3 分鐘就沒有決賽成績；否則以中位數計分。之後至少最快的 10 個作品會在同一台閒置機器上單獨重新計時 7 次，其中位數取代第一次的分數。

截止時間：週日上午 11:00 EST。
